# AI智能审图工作流 v6.0 — 专业视角审视报告

## 一、审视方法

**参照系**：实际建筑工程从设计到施工的全生命周期流程  
**审视维度**：审图机构、设计院、施工单位三视角综合  
**审视对象**：v6.0 工作流的流程逻辑、规则覆盖、数据结构、输出质量

## 二、实际建设过程 vs 当前工作流对照

### 2.1 实际建设全流程（专业参照系）

```
阶段0: 前期条件
  ├── 立项批复、用地规划许可
  ├── 地质勘察报告
  └── 方案设计审查通过

阶段1: 建筑专业（先导专业）
  ├── 总平面图 → 用地红线、建筑退让、消防车道
  ├── 建筑设计说明 → 基本参数、耐火等级、节能等级
  ├── 各层平面图 → 功能布局、防火分区、疏散体系
  ├── 立面/剖面图 → 建筑高度、层高、标高体系
  └── 构造详图 → 防水、保温、节点做法

阶段2: 结构专业（基于建筑条件）
  ├── 结构设计说明 → 安全等级、抗震参数、荷载取值
  ├── 基础图 → 地基处理、基础选型
  ├── 各层梁板柱图 → 构件布置、截面配筋
  └── 节点详图 → 钢筋锚固、连接构造

阶段3: 机电专业（基于建筑+结构条件）
  ├── 暖通 → 防排烟、空调、通风系统
  ├── 给排水 → 消防给水、喷淋、生活给排水
  ├── 电气 → 强电配电、照明、消防报警
  └── 智能化 → 弱电系统、楼宇自控

阶段4: 综合协调（跨专业）
  ├── 管线综合排布（BIM碰撞检测）
  ├── 竖井布置、吊顶空间协调
  ├── 预留预埋件（套管、洞口）
  └── 设备机房布置

阶段5: 施工落地
  ├── 施工工艺可行性
  ├── 材料采购可行性
  └── 运维检修便利性
```

### 2.2 当前工作流的问题诊断

#### 问题1：流程顺序不符合建设逻辑

```
实际建设顺序：                    当前工作流顺序：
  建筑（先导）                       Step 1: DXF提取（无差别）
  结构（承接建筑）                    Step 2: 强条审查（无差别扫描）
  机电（承接建筑+结构）               Step 3: 错漏排查（无差别扫描）
  综合协调                           Step 4: 跨专业校验
  施工落地                           Step 5: 工程分析

问题：当前流程是"扁平化"的，所有专业一锅端，
     没有体现专业间的依赖关系和审查优先级。
```

**实际影响**：审查报告无法告诉用户"先改什么、后改什么"，所有问题平铺罗列，缺乏优先级和依赖关系。

#### 问题2：缺少"项目级参数锚定"环节

```
实际审图第一步：
  审图师拿到图纸后，首先确认"项目基本参数"——
  建筑高度、层数、耐火等级、抗震设防、建筑面积...
  这些参数是所有后续审查的"锚点"。

当前工作流：
  没有独立的"参数锚定"步骤。
  项目参数分散在262条规则中各自搜索，
  如果某张图纸缺少关键参数，不会在早期被发现，
  而是在后续各步骤中反复报"未找到证据"。
```

#### 问题3：缺少"楼栋→楼层"的空间维度

```
实际建设逻辑：
  项目 → 楼栋（1号楼、2号楼...）
       → 楼层（地下室、1层、2层...）
       → 专业系统
       → 构件

当前工作流：
  所有图纸平铺处理，没有空间层级。
  无法回答"1号楼3层走廊净高够不够"这种具体问题。
  碰撞检测缺少空间定位（哪一层、哪个轴线交叉点）。
```

#### 问题4：规则检查方式单一

```
当前方式：关键词搜索 + 正则匹配
  只能判断"图纸中是否提到了某参数"
  无法判断"参数值是否正确"

举例：
  规则"疏散宽度应满足计算要求"
  当前：搜索到"疏散宽度"关键词 → 判定"合规"
  实际：需要知道疏散人数 → 查表得宽度要求 → 对比图纸标注值

差距：当前是"存在性检查"，不是"合规性验证"
```

#### 问题5：跨专业校验缺少"版本一致性"

```
实际常见问题：
  建筑改了防火分区划分，但暖通、给排水、电气的图纸
  还是旧版本的防火分区。当前跨专业校验只检查
  "各专业是否都提到了防火分区"，不检查"划分是否一致"。
```

## 三、逐级拆解图纸 — 专业审查框架

### 3.1 拆解逻辑

```
Level 0: 项目锚定
  └── 提取并交叉验证项目基本参数（唯一真相源）

Level 1: 楼栋拆解
  └── 按楼栋分组图纸（1号楼、2号楼、地下室...）

Level 2: 楼层拆解
  └── 按楼层分组（B1层、1层、2层...标准层、屋面层）

Level 3: 专业系统拆解
  └── 每个楼层内的各专业图纸（建筑平面、结构梁板、机电管线）

Level 4: 构件级审查
  └── 具体构件的参数校验（梁截面、管线规格、设备选型）

Level 5: 交叉碰撞
  └── 同一空间内多专业构件的空间冲突检测
```

### 3.2 与当前工作流的映射关系

```
当前工作流（扁平）              逐级拆解框架（层级）
─────────────────────          ──────────────────────
Step 1: DXF提取               → Level 0-2: 锚定+楼栋+楼层
Step 2: 强条审查(262条)        → Level 3-4: 专业系统+构件级
Step 3: 错漏排查               → Level 4-5: 构件级+碰撞
Step 4: 跨专业校验(22项)       → Level 5: 交叉碰撞
Step 5: 工程分析               → Level 4: 施工可行性
```

## 四、关键改进点详述

### 4.1 新增 Phase A: 项目锚定

**目的**：在审查开始前，先建立"项目参数字典"，作为后续所有审查的唯一参照。

**锚定参数清单**：

| 参数类别 | 具体参数 | 来源专业 | 验证逻辑 |
|---------|---------|---------|---------|
| 建筑基本 | 建筑高度、层数、面积 | 建筑 | 建筑=结构=暖通=给排水=电气 |
| 消防安全 | 耐火等级、防火分区数量 | 建筑 | 建筑=结构=暖通=给排水=电气 |
| 结构安全 | 抗震设防烈度、安全等级、设计使用年限 | 结构 | 结构=电气（抗震支吊架） |
| 气候条件 | 基本风压、基本雪压 | 结构 | 结构=建筑（节能计算） |

**输出**：`project_anchor.json`

```json
{
  "project_name": "XX项目",
  "buildings": [
    {
      "name": "1号楼",
      "floors_above": 6,
      "floors_below": 1,
      "height_m": 23.95,
      "fire_rating": "二级",
      "seismic_intensity": 6,
      "structural_system": "框架结构",
      "floor_heights": {
        "B1": 4.5, "1F": 4.5, "2F-6F": 3.9
      }
    }
  ],
  "cross_validation": {
    "height": {"建筑": 23.95, "结构": 23.95, "暖通": 24.0, "status": "need_verify"},
    "fire_rating": {"建筑": "二级", "结构": "二级", "电气": "二级", "status": "compliant"}
  }
}
```

### 4.2 新增 Phase B: 楼栋-楼层拆解

**目的**：建立空间索引，让后续审查结果可以精确定位到具体楼层。

**拆解逻辑**：

```
输入：所有 *_unified.json 文件
  ↓
按文件名关键词分组：
  "1号楼" → building_1/
  "2号楼" → building_2/
  "地下室" → basement/
  ↓
按楼层关键词分组：
  "地下室" → B1/
  "一层" / "1层" / "首层" → 1F/
  "二层" / "2层" → 2F/
  "标准层" / "3~6层" → 3F-6F/
  "屋面" / "屋顶" → RF/
  ↓
按专业分类：
  "建筑" → arch/
  "结构" → struct/
  "暖通" → hvac/
  "给排水" → plumbing/
  "电气" → elec/
```

**输出**：`spatial_index.json`

```json
{
  "1号楼": {
    "B1": {
      "arch": ["建筑-地下室平面_unified.json"],
      "struct": ["结构-地下室底板_unified.json"],
      "hvac": ["暖通-地下室防排烟_unified.json"],
      "plumbing": ["给排水-地下室消防_unified.json"],
      "elec": ["电气-地下室照明_unified.json"]
    },
    "1F": { ... }
  }
}
```

### 4.3 改造 Phase C: 专业内审查

**改进点**：将当前262条规则的"无差别扫描"改为"按专业分组、按楼层定位"。

```
当前方式：
  262条规则 × 所有文件 = 262次全文搜索

改进方式：
  对每个楼栋的每个楼层：
    建筑专业图纸 → ARCH-001~030 (30条)
    结构专业图纸 → STR-001~025 (25条)
    暖通专业图纸 → HVAC-001~033 (33条)
    给排水专业图纸 → PLB-001~033 (33条)
    电气专业图纸 → ELE-001~043 (43条)
    ...
```

**优势**：
- 审查结果可定位到"1号楼3层建筑平面图"
- 可按专业生成子报告
- 可识别"某楼层缺少某专业图纸"

### 4.4 改造 Phase D: 跨专业校验

**新增检查项**：

| 检查项 | 说明 | 当前状态 |
|--------|------|---------|
| 防火分区版本同步 | 建筑改了分区，其他专业是否同步 | ❌ 缺失 |
| 图纸版本一致性 | 检查图纸日期、版本号是否一致 | ❌ 缺失 |
| 预留洞口清单 | 结构留洞 vs 机电穿管需求 | ❌ 缺失 |
| 竖井空间分配 | 多专业共用竖井的空间分配 | ❌ 缺失 |
| 设备房尺寸 | 建筑给的机房尺寸 vs 机电设备需求 | ❌ 缺失 |

### 4.5 改造报告输出

**当前**：3份报告（强条/错漏/跨专业），问题平铺罗列

**改进**：按空间层级组织报告

```
报告结构：
├── 项目概况（参数锚定结果）
├── 1号楼
│   ├── 地下室B1
│   │   ├── 建筑专业问题 (3条)
│   │   ├── 结构专业问题 (1条)
│   │   ├── 机电碰撞问题 (2条)
│   │   └── 跨专业一致性问题 (1条)
│   ├── 1层
│   │   ├── ...
│   └── 标准层(2-6层)
│       ├── ...
├── 2号楼
│   └── ...
├── 问题优先级排序
│   ├── 严重 (必须整改)
│   ├── 重要 (应整改)
│   ├── 一般 (建议整改)
│   └── 提示 (供参考)
└── 整改建议（含依赖关系）
    ├── 第1批：建筑参数修正 → 触发结构/机电联动修改
    ├── 第2批：结构构件调整 → 触发机电管线避让
    └── 第3批：机电管线优化
```

## 七、总结

### 一句话评价

> 当前 v6.0 是一套**规则覆盖全面、证据链严谨**的审查系统，但流程逻辑是**扁平化**的，缺少实际建设过程中的**层级关系**和**依赖顺序**。核心改进方向是：**从"无差别扫描"升级为"逐级拆解、逐级审查"**。

### 改进核心公式

```
当前：  所有图纸 → 所有规则 → 所有问题（平铺）

改进：  项目锚定 → 楼栋拆解 → 楼层拆解 → 专业审查 → 跨专业校验 → 施工分析
        (唯一真相源)  (空间索引)  (定位)    (分组)     (碰撞)      (落地)
```
