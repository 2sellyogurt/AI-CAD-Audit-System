## 一、模型输出质量：LLM生成内容完整性校验

### 1.1 问题现象

AI模型在生成分析报告时，高频出现以下三类缺陷：

| 缺陷类型 | 表现 | 频率 |
|----------|------|------|
| **占位符泄漏** | 输出中出现 `第XX页`、`第X.X.X节`、`TBD` | 高 |
| **证据链空洞** | "与规范要求不符"但无具体数值比对 | 高 |
| **模板化套话** | "核对图纸""确认是否设置"等泛化修改建议 | 极高 |

### 1.2 根因分析

```
┌──────────┐    ┌──────────────┐    ┌────────────┐
│ 输入数据  │───→│ LLM 推理      │───→│ 最终输出    │
│ 字段缺失  │    │ 无占位符检测  │    │ 含 XX/TBD  │
│ 精度不足  │    │ 无证据链校验  │    │ 空洞结论    │
└──────────┘    └──────────────┘    └────────────┘
```

根本原因：**LLM输出缺乏结构化后处理校验层**。模型倾向于在信息不足时"礼貌性填空"而非"坦诚说不知道"。

### 1.3 本项目验证

> **验证等级：✅ 充分证实**

在智能审图系统v6.0项目中，上述三类缺陷全部命中原型系统：

| 缺陷类型 | 本项目实际表现 | 量化数据 |
|----------|---------------|---------|
| 占位符泄漏 | 封面/概况/签字栏中项目名称显示"未命名项目" | 9个输出文件100%出现 |
| 证据链空洞 | "待核实""核对图纸"无具体数值支撑 | 初期75/201条(37%) |
| 模板化套话 | "确认是否设置""核对图纸"占整改建议的绝对多数 | 消防报告12条强标中5条 |

**修复尝试**：
- 在rule_checker中增加 `_extract_context_with_numbers()`，从DXF文本中提取关键词周围100字符上下文作为evidence
- 在polisher中将表格重构为"图纸现状 | 规范要求 | 应该如何"三列
- 修复后证据从空字符串变为有文本片段，但质量仍参差不齐

**遗留问题**：证据是非结构化文本，无法自动做数值比对。例如"面积"二字不能回答"图纸上标注的面积具体是多少"。

### 1.4 优化方案

```
                 ┌─────────────────────┐
LLM 输出 ──────→│ 占位符正则扫描        │
                 │ (XX|TBD|TODO|N/A)    │
                 └──────┬──────────────┘
                        │ 过滤
                 ┌──────▼──────────────┐
                 │ 证据链完整性校验      │
                 │ (具体数值? 坐标定位?) │
                 └──────┬──────────────┘
                        │ 过滤
                 ┌──────▼──────────────┐
                 │ 模糊建议检测          │
                 │ ("核对"/"确认"/"建议")│
                 └──────┬──────────────┘
                        │
                 ┌──────▼──────────────┐
                 │ 降级决策:             │
                 │ 通过→正常输出         │
                 │ 阻断→标记"待人工确认"  │
                 └─────────────────────┘
```

**关键配置**：

```python
# 占位符检测正则
PLACEHOLDER_PATTERNS = [
    r'第[Xx]{1,3}页',           # 第XX页
    r'第\d+\.\d+\.\d+节',       # 第X.X.X节
    r'\bTBD\b',
    r'\bTODO\b',
    r'[（(]待补充[）)]',
    r'未命名',                   # ← 本项目新增
    r'未知文件',                 # ← 本项目新增
]

# 空洞结论关键词（本项目验证命中率极高）
HOLLOW_CONCLUSION_KEYWORDS = [
    '核对图纸', '确认是否', '详见相关规范',
    '根据实际情况', '按设计要求',
    '确认是否设置',               # ← 本项目新增
    '确认是否具备',               # ← 本项目新增
]
```

**预期效果**：将占位符泄漏率从 ~30% 降至 <1%，空洞结论率从 ~60% 降至 <15%。

**本项目实际效果**：修复前空洞结论37% → 修复后约20%。

## 二、规则/知识库的真实覆盖率

### 2.1 问题现象

声称"覆盖 N 条规则/知识条目"，实际核心规则库仅包含其中的极小比例。其余规则要么分布在尚未加载的子模块中，要么以模板形式存在但推理时未激活，要么属于"框架预留"但未实现判断逻辑。

### 2.2 本项目验证

> **验证等级：✅ 充分证实（本项目的最佳验证案例）**

智能审图系统v6.0项目中发现了教科书级别的"虚假覆盖率"问题：

| 规则库 | 规则数 | 实际状态 |
|--------|--------|---------|
| 主规则库 `rules.json` | 264 | ✅ 被引擎加载并使用 |
| 分专业规则库 `config/rules/*.json`（7文件） | **6088** | 🔴 **死数据，无任何引擎加载** |
| BIM合规规则库 `compliance_rules.json` | 30 | 🟡 独立引擎加载，与主引擎割裂 |
| **合计声称** | 6382 | — |
| **合计实际激活** | **264** | **实际覆盖率仅4.1%** |

**关键发现**：

```
声称覆盖: 6382条规则
实际激活: 264条规则
真实覆盖率: 4.1%

6088条规则按建筑/结构/给排水等7个专业拆分，格式规范、内容完整，
但 rule_checker.py 的加载路径只指向 rules.json，
config/rules/ 目录从未出现在任何 import 或 load 语句中
→ 6088条规则是纯粹的"文件体积"，对模型推理贡献为 0
```

**264条活跃规则的激活分析**：

| 状态 | 数量 | 占比 |
|------|------|------|
| 规则总数 | 264 | 100% |
| 实际触发（匹配到关键词） | 201 | 76.1% |
| 判定"合规" | 113 | 42.8% |
| 判定"待核实" | 84 | 31.8% |
| 判定"不合规" | 4 | 1.5% |
| 完全未触发 | 63 | 23.9% |

24%的规则从未匹配到任何关键词，属于"存在但场景不适用"。

### 2.3 优化方案

**规则覆盖率禁止统计"已定义总数"，强制改为"已激活且可触发总数"**：

```
统计口径定义:
  已定义:  配置文件中有条目         ← 禁止用于对外报告
  可加载:  import + parse 成功      ← 内部度量可用
  已激活:  推理时被实际触发过        ← 对外报告唯一允许口径
```

**本项目已执行的修正**：

| 动作 | 效果 |
|------|------|
| 删除16条消防版本重复规则 | 280→264条 |
| 16条关键规则增加exclude_keywords | 消防误报65→4条(↓94%) |
| 每轮step5后输出激活统计 | 可追踪每条规则的触发状态 |

**遗留问题**：6088条死数据待激活或清理。

## 三、模型管线：中间数据质量校验

### 3.1 问题现象

管线的关键中间步骤产出为空值/默认值，但下游节点未校验直接消费，导致最终输出看似完整实则不可用：

```
上游输出: 楼层 = "未知" (100%数据)
下游消费: 直接使用"未知"生成楼层分布报表
最终呈现: 报表格式完整，但信息含量为0
```

### 3.2 本项目验证

> **验证等级：✅ 充分证实（三条质量传播链全部命中原型系统）**

**链路1：项目元信息→报告封面**

```
step0: project_name = "" → step5引擎 → polisher → 封面显示"未命名项目"
影响: 9个文件100%受影响
```

**链路2：DXF文本→evidence字段**

```
DXF解析(62000+行) → 关键词匹配 → evidence = 关键词周围文本
→ 强条项: evidence = "面积"(仅2字，无实际数值)
→ 强标项: evidence = 长文本(含噪音，需人工筛选)
影响: 无法自动数值比对，人工核对仍需回归DXF原文
```

**链路3：building_type→规则匹配过滤（经典案例）**

```
初始值: building_type = "公建"
→ GB 50099(中小学规范)错误匹配医科大学项目
→ 修复: building_type = "大学" + 规则标注["中小学"]
→ 效果: 消防误报 65→4条(↓94%)
```

### 3.3 优化方案

**在管线DAG中植入数据质量门（Data Quality Gate）**：

```python
# 每个阶段输出必须附带 self-check 结果
class StageOutput:
    result: Any
    quality: QualityMetrics  # 必须字段

@dataclass
class QualityMetrics:
    null_rate: float          # 关键字段空值率
    default_rate: float       # 回退默认值使用率
    coverage: float           # 数据覆盖率
    passed: bool              # 是否通过质量门

if stage_output.quality.null_rate > 0.8:
    raise DataQualityError(f"Stage {stage} degraded")
```

**本项目建议阈值**：

| 检测字段 | 阈值 | 本项目实际 |
|----------|------|-----------|
| 关键字段空值 | >0% 阻断 | project_name 100%空 |
| 建筑类型模糊值 | "公建""未知"阻断 | 初始"公建"已修复 |
| evidence有效长度 | <10字符降级 | "面积"仅2字符 |
| 强制规则命中率 | >30%告警 | 修复前65% |

## 四、输出产物：区分三级置信度

### 4.1 问题现象

所有模型输出被同等呈现，未区分AI自动判定与人工确认的结论。用户无法判断哪些结论可以直接采纳，哪些需要二次确认。

### 4.2 本项目验证

> **验证等级：✅ 充分证实（polisher实现部分区分）**

本项目在polisher中实现了初步的三级区分：

| 等级 | 判定条件 | 本项数量 | 报告呈现 |
|------|---------|---------|---------|
| 🔴 强条违反 | status="不合规" + is_mandatory | 4条 | "违反强制性条文"章节 |
| 🟡 强标待核实 | status="待核实" + is_mandatory | 75条 | "违反强制性标准"章节 |
| ⚪ 建议项 | status="合规" | 113条 | "其它（建议性问题）" |

**尚缺**：显式的🟢🟡🔴置信度标签，以及"此结论基于关键词匹配，未经人工复核"等说明。

### 4.3 优化方案

**输出产物强制标注三级置信度标签**：

| 等级 | 条件 | 呈现方式 |
|------|------|---------|
| 🟢 高置信 | 数据完整 + 规则精确命中 + 无歧义 | 可直接采纳 |
| 🟡 中置信 | 数据部分缺失或规则为模糊匹配 | 建议参考，需人工确认 |
| 🔴 低置信 | 关键数据缺失或使用默认推断 | 仅供参考，不可作为判定依据 |

**禁止行为**：将低置信度输出与高置信度输出混合排列在同一列表中且不加区分标签。

## 五、性能基准：合成测试 vs 生产场景的鸿沟

### 5.1 问题现象

性能报告指标（如"每秒处理 N 万元素"）与实际业务场景严重脱节：

| 指标来源 | 测试数据 | 业务真相 |
|----------|---------|---------|
| 合成基准测试 | 性能指标极高 | 未包含IO开销 |
| 数据规模 | 模拟小批量 | 生产数据量级差异大 |
| 环境 | 理想单机 | 生产有噪声与资源竞争 |

### 5.2 本项目关联

> **⚠️ 本项目为离线批处理，未内置性能采集。但存在潜在关联：**

step5当前处理6万+行DXF数据 + 264条规则，耗时20-30秒。如果扩展到6088条规则或更大图纸，`keywords * texts` 的O(n²)匹配将成为瓶颈。

### 5.3 优化建议

**性能报告强制标注数据来源**：

```markdown
每个性能数字必须附带三重标签：
  [数据来源: 合成 / 历史回放 / 生产采样]
  [数据规模: <具体数量>]
  [环境: 开发机 / 预发布 / 生产]
```

**禁止行为**：将合成基准测试结果作为"系统性能指标"写入交付报告且不标注数据来源。

## 六、新增发现：多规则库并存与Schema割裂

### 6.1 问题定位

在本次项目实践中，新发现一个原建议中未覆盖的系统性问题：

```
三套规则库并存于同一项目中：
┌─────────────────┐  ┌──────────────────┐  ┌─────────────────────┐
│ rules.json       │  │ config/rules/*.   │  │ compliance_rules.   │
│ (264条活跃)      │  │ json(6088死数据)  │  │ json(30条半活跃)     │
│ Schema: 顶层数组  │  │ Schema: 顶层数组  │  │ Schema: 嵌套结构     │
│ 被RuleChecker加载 │  │ 无引擎加载       │  │ 被独立引擎加载       │
└─────────────────┘  └──────────────────┘  └─────────────────────┘
```

**三个Schema完全不兼容**：字段名、嵌套层级、加载方式均不同。两个引擎输出无法直接合并，polisher需分别解析后拼接。

### 6.2 优化建议

1. **统一规则库Schema**：选择一套Schema作为标准，迁移所有规则
2. **建立规则加载注册表**：启动时扫描所有规则源，输出"已加载/未加载"清单
3. **废弃死数据**：不使用的规则文件应删除或归档
