# AI智能审图系统 v7.0 — 项目介绍（UI设计基础文档）

## 一、项目身份

| 项目 | 值 |
|------|-----|
| 产品名称 | **AI智能审图系统 v7.0** |
| 产品定位 | 面向建筑行业设计图纸的AI自动化审查与工程合理性评估平台 |
| 对标场景 | 监理工程师/设计审查师的施工图审查工作 |
| 核心价值 | 将人工3-5天的图纸审查压缩到10分钟，同时提供条文合规+工程最优性双维度评估 |
| 当前版本 | v7.0（LLM代理审查模式，零外部API依赖） |

### 2.2 审查维度（三维评估体系）

```
维度1: 条文符合性（传统审查）
  ├─ A级（强条违反）：26项 — 必须整改
  ├─ B级（重要）：37项 — 建议整改
  ├─ C级（一般）：23项 — 提示关注
  └─ D级（提示）：3项 — 信息补充

维度2: 工程合理性（v7.0新增）★
  ├─ R0（0~30分）：设计不可行
  ├─ R1（30~55分）：合规但非最优
  ├─ R2（55~80分）：基本合理
  └─ R3（80~100分）：设计优秀

维度3: 跨专业一致性
  └─ 建筑-结构-暖通-电气-给排水之间的交叉校验
```

## 四、产出物（三份报告）

| 报告 | 内容定位 | 目标用户 |
|------|---------|---------|
| **场景1：基础错漏排查报告** | 逐专业列出所有图纸质量问题，含空间冲突验证 | 专业设计师/项目经理 |
| **场景2：跨专业一致性校验报告** | 建筑-结构-机电之间的接口矛盾与碰撞消解 | 设计总负责人/技术总监 |
| **场景3：强条合规性审查报告** | 国家标准强制性条文逐条对标+工程合理性评估 | 审图机构/业主方 |

每份报告格式：docx（含表格/分级标题/规范引用），可直接打印归档。

## 五、技术架构概要

```
用户层:  Web UI / 桌面客户端（待开发）
          ↓
API层:   REST API / 命令行入口
          ↓
引擎层:  ├─ llm_full_review.py   (LLM代理审查主引擎)
          ├─ rationality_engine.py (合理性评估引擎)
          ├─ spatial_reasoning.py  (空间推理引擎)
          └─ unified_pipeline.py   (统一管线调度)
          ↓
数据层:  ├─ text_extracts/  (DXF文本提取)
          ├─ spatial_conflicts_v5.json (空间冲突)
          └─ uai_review_data.py (专家知识库)
          ↓
输出层:  场景1/2/3 .docx 报告
```

**核心特点**：
- LLM代理模式：零外部API Key依赖，AI直接分析图纸文本
- 插件式专业模块：每专业独立审查函数，新增专业只需添加一个函数
- 合理性引擎：可独立运行的评分模块，与审查主流程解耦

## 七、数据流与状态管理

### 7.1 审查任务状态机

```
[新建] → [上传中] → [预处理中] → [审查中] → [合理性评估中] → [生成报告中] → [已完成]
                           ↘        ↘                         ↗
                          [失败]   [部分完成]（可查看已完成的专业）
```

### 7.2 核心数据实体

```
Project (项目)
├─ id, name, location, building_type
├─ created_at, status
└─ drawings: [Drawing]

Drawing (图纸)
├─ filename, discipline, size
├─ text_extract_path
└─ status

ReviewTask (审查任务)
├─ project_id
├─ disciplines: [string]  # 勾选的专业
├─ depth: "quick"|"standard"|"deep"
├─ progress: {discipline: status}
└─ results: [Finding]

Finding (审查发现)
├─ id, discipline, severity (A/B/C/D)
├─ standard, finding_text, fix_text
├─ rationality: {level, score, explanation}
└─ related_spatial_conflicts: [id]

SpatialConflict (空间冲突)
├─ id, type, severity
├─ confidence: "high"|"medium"|"low"
├─ involved_files: [string]
├─ floor, description, risk
└─ is_false_positive: bool

Report (报告)
├─ scene: "1"|"2"|"3"
├─ format: "docx"
├─ file_path, file_size
└─ generated_at
```

## 九、UI设计要点

1. **信息密度控制**：89项问题分页展示，默认每页20条，避免信息过载
2. **颜色语义**：A级=红 #E74C3C，B级=橙 #F39C12，C级=黄 #F1C40F，D级=灰 #95A5A6；R0=深红，R1=橙色，R2=绿色，R3=蓝色
3. **渐进式披露**：问题列表→点击展开详情→详情中嵌套合理性评估→相关图纸链接
4. **快捷筛选**：预设"只看A级""只看R1""只看结构专业"等一键筛选按钮
5. **离线友好**：系统无需外部API，审查可完全本地运行
6. **响应式布局**：移动端可查看报告摘要，PC端完整功能
7. **导出格式**：docx（正式归档）、PDF（分发审阅）、JSON（API对接）
